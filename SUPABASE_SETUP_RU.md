# Общая база и режим администратора — настройка Supabase

В приложении остаётся локальная летопись для удобства игрока, а действия дополнительно отправляются в общую базу. Администратор видит общую очередь событий (молитвы, запросы, благословения, контракты, изменения регионов и армий, выбранные тактики и результаты боёв), а игрок — ответы на обращения, отправленные из своего браузера. Полные локальные сохранения игроков между пользователями не синхронизируются; администратору доступен журнал событий, а не чужой localStorage.

## 1. Создать проект

1. Создайте проект на https://supabase.com/.
2. В Authentication → Providers включите **Anonymous Sign-Ins** и **Email** (Email/Password).
3. Проверьте лимиты Authentication для анонимного входа. Supabase рекомендует CAPTCHA/Turnstile для публичных проектов. В этой версии клиент ещё не передаёт CAPTCHA token, поэтому пока не включайте обязательную CAPTCHA-проверку: сначала нужно добавить виджет и его публичный site key в интерфейс.
4. В SQL Editor запустите весь файл `supabase/schema.sql` из этого архива.
5. В Authentication → Users создайте пользователя администратора с вашим email и сильным паролем. Если включено подтверждение адреса, подтвердите email.
6. Скопируйте UUID этого пользователя и назначьте ему роль владельца запросом:

```sql
insert into public.lotw_admins(user_id, role)
values ('UUID_ВАШЕГО_ПОЛЬЗОВАТЕЛЯ', 'owner')
on conflict (user_id) do update set role = 'owner';
```

## 2. Подключить публичный ключ

1. В настройках Supabase откройте Project Settings → API.
2. Скопируйте Project URL и публичный `anon` / publishable key.
3. В файле `backend-config.js` заполните `url` и `anonKey`.
4. Загрузите этот файл в репозиторий вместе с обновлением.

**Никогда не помещайте `service_role` / secret key или пароль администратора в HTML, JavaScript, GitHub Pages или этот файл.** Доступ ограничивается RLS-политиками базы: игрок может вставить только собственную новую запись, читать только свои записи и не может сам выдать себе статус или ответ; читать общую очередь и менять записи может только учётная запись с ролью `admin` или `owner`. Пароль администратора вводится только в форме входа; админская сессия хранится отдельно от анонимной сессии игрока и действует до перезагрузки страницы — после перезагрузки администратор входит снова.

## 3. Как работает идентификация игроков

При первом запуске на конкретном браузере создаётся анонимная Auth-запись. Её UUID связывает действия этого браузера с ответами администратора. Имя игрока вводится в верхней панели и прикрепляется к действиям. Анонимная учётная запись не является восстановимым логином: после очистки хранилища браузера, выхода из аккаунта или перехода на другое устройство игрок не сможет вернуться в прежнюю анонимную учётную запись и получит другой UUID. Для постоянной идентичности понадобится отдельная регистрация или привязка email. Для публичного запуска рекомендуется дополнительно подключить CAPTCHA/Turnstile (после добавления token-виджета в клиент) и наблюдать за лимитами анонимного входа.

## 4. Проверка

- Игрок отправляет обычную молитву или запрос необычного месторождения.
- Владелец открывает «Режим администратора», входит по email и паролю и видит общий список.
- Администратор отвечает и выбирает статус «Одобрено», «Отклонено», «Нужны сведения» или «Отвечено».
- Игрок видит ответ в блоке «Ответы Владыки» на главной странице.

В общую очередь попадают только новые действия, совершённые после подключения Supabase. Старые локальные журналы автоматически не переносятся. Если Supabase не настроен, приложение продолжает работать локально, но межпользовательская синхронизация и админ-вход не активируются.
